## 2. Behavior changes beyond the markup

- **Confidence carries over within a set.** `wirePractice` used to wipe `ps.conf` after every answer, so the second
  question of a set could not be answered until a chip was pressed again. The contract's set flow (answer, Next, answer,
  Finish) needs the second answer to go through, so the rating now persists.

    the keyboard is gated the same way.

  (`!S.ps.done`), so the tutor is not told about a question that is no longer on screen.

  picked option.

## 4. Open: `renderPractice.whyMatches` (CONTRACT-PROBLEM)

`probe_repro.js` practice section:
`Object.assign(res, clickWrongAndReadWhy(".qopt", q.w ? q.w[otherQ] : ""))`.

- **What the probe compares.** `otherQ` is the first wrong, un-picked option in `q.o` (load) order.
- **What the probe clicks.** `clickWrongAndReadWhy` clicks `others[0]`, the first dim option in **DOM** order.
- **Why they differ.** Practice deliberately shows options in a per-serve display order (`viewOrder`, the permutation
  the probe's own `bias` section measures). In rapid and spot the DOM order equals the data order, so there the two
  coincide.
- **On the stub.** For `en5q01` the screen shows orig 1, 4, 3, 0, 2 as A–E, and the pick is orig 1. The probe clicks
  orig 4 (5'-deiodinase) and compares the revealed text with the note for orig 2 (tyrosine hydroxylase). That scores
  0 shared words, although the note revealed is exactly `q.w[4]`.
- **Across the stub.** The same mismatch hits 4 of the 6 stub questions.
- **On real content.** The field would pass or fail by the luck of each bank's permutation.
- **The only engine-side way to pass it.** Drop or neutralize the display shuffle on first serve. That would work around
  the check rather than meet it, so it was not done.
- **Suggested gate fix.** Compare against the note of the button actually clicked. For example, let
  `clickWrongAndReadWhy` accept a function of the clicked button and pass
  `function(b){ return q.w ? q.w[+b.dataset.opt] : ""; }` for practice. Alternatively, put the `[data-opt="<otherQ>"]`
  button first in `others`.

## 5. Previously-missed fix (reopened 2026-09-28)

**The finding (P2.6 redo, F23/F24).** "Previously missed" (`startSet("due")`) served questions due on the spacing
ladder, or a random 20 when none were due. The branch meant for wrong answers was dead code, and it served a question
that had been answered right.

**Cause.** `startSet` had two `k==="due"` branches. The first (spacing-due, with a random fill) always won. The second
(`!ok`, the missed rule) could never run. The practice button labelled "Previously missed" sent `due`, and so did the
plan's "N questions are due again" row. Every other named set also ended with
`if(!set.length) set = shuffle(QS).slice(0,20)`, so an empty "Verify", "Never attempted" or "Target my weak spots" set
served 20 random questions under its own label.

**Files changed:** `engine/engine.js`, `engine/ENGINE-GLOBALS.md` (the QS and RAPID rows name `practicePool` /
`rapidPool`).

### 5.1 The rule for each set (one definition, used by every label and by what is served)

`practicePool(k)` and `rapidPool(k)` define each named set. `startSet` / `startRapid` serve `practiceSet` / `rapidSet`,
which apply the order and the cap to that pool. Every count on screen comes from `setCount`, which reads the same pool:
the practice and rapid buttons, the plan's verify / weak / due-again rows, and the Weak Spots buttons. So a label's
count is the number served. It reads "(n)", or "(n of m)" when the cap holds some back. "High yield only" filters
before the cap.

State used: `S.qs[id]` is rewritten by every answer (`wirePractice`), so `rec.ok` is the result of the **most recent**
answer. `rec.due` is its place on the spacing ladder: a miss restarts at box 1 (about 15 min). `rec.verified` /
`rec.verifyDue` drive the verify set.

| Set (label) | Rule | Order, cap |
|---|---|---|
| Previously missed (`missed`, new key) | answered, and the most recent answer is wrong (`!rec.ok`): a miss not since answered right. Answering it right removes it; missing it again keeps it | earliest `due` first. Every miss restarts at the 15-minute box, so the miss that has waited longest comes first and one made a minute ago comes last. Cap 20 |
| Due for review (`due`, the plan row "N questions are due again") | answered, `box > 0`, `due <= now`, right **or** wrong: spaced review | most overdue first, cap 20 |
| Verify my "correct" answers (`verify`) | most recent answer right, not yet `verified`, `verifyDue <= now` | shuffled, cap 20 |
| Target my weak spots (`weak`) | on a topic `diagnose()` flags, and never answered or last answered wrong. **No fallback:** it used to take the top five topics by priority when nothing was flagged | shuffled, cap 20 |
| Never attempted (`unseen`) | no record | shuffled, cap 20 |
| Everything, shuffled (`all`) | every question | shuffled, all |
| Rapid: Linked queue | this block's items in `S.linked` (a practice miss adds them; a right rapid answer removes one) | shuffled, cap 40 |
| Rapid: Due now | `hubDue()`: every block's due items, most overdue first. When the hub is empty, this block's `isDue` items. The count used to be this block's due items while the set served the hub's | as listed, cap 40 |
| Rapid: From my weak spots | items on flagged topics. **No fallback** (it used to fall back to due, then to all) | shuffled, cap 40 |
| Rapid: All N, shuffled | every item. It used to serve 40 under "All N"; now it serves all N ("N high-yield" when that filter is on) | shuffled, all |
| Builder (`custom`) | unchanged; its "Start N" count was already `bldOrdered`. Status "Got wrong" is the same `!rec.ok` rule as Previously missed. The **"My weak spots"** topic shortcut now selects the flagged topics only, shows their number and is disabled at 0. It used to select the top five topics by priority | as chosen |

**An empty set says so.** `startSet` / `startRapid` never fill an empty set. They set `SET_EMPTY` and show the index

- The notice clears on the next navigation (`go`) or on the next set that starts.

## 7. Stale linked-queue ids pruned (orchestrator follow-up, 2026-09-28)

**Problem (open note (a) of §6).** `S.linked` could keep ids whose rapid item had left the content. Editing a rapid
question changes its content-derived id, and a restored or merged save can carry old ids. Such an id is never served
(`rapidPool("linked")` filters `RAPID`), so it is never answered and never drained. It kept the plan's linked row
showing, and costed through `linkedN` in `stageAllot` / `planDaysLeft`, for items that could not be served.

**Fix.**
- **`repairState`** (`engine/engine.js`) now rewrites `S.linked` as a clean queue. It keeps only strings that are own
  keys of `RBYID` (this block's rapid items; `hasOwnProperty`, so an inherited key such as "constructor" cannot
  pass). It drops repeats and keeps queue order. A missing or non-array value becomes `[]`.
  - `repairState` runs on load (after `migrateRapidKeys` maps the old numeric ids), after a db merge, and before
    every render.
  - So the plan, the pacing math, the self-test's `paceHeader` and the Linked queue button all see the pruned length.
- **The pacing code is unchanged.** It still reads `S.linked.length`, which can now only count servable items.
- **Self-test.**
  - New section `linkedPrune`, asserted with `must("linkedPrune", …)`.
  - It seeds `["zz-stale-id", b, a, b, "constructor", 7]` and runs `repairState`. It expects exactly `[b, a]`: the
    stale id, the inherited key, the number and the repeat all go, and the order stays.
  - It then seeds a queue of one stale id and expects it emptied, with no `linked` row in `todaysPlan()`.
  - It is skipped, with the reason, when the content has no rapid items.
  - `paceHeader`'s "with review" variant used to seed `S.linked = ["zz0","zz1"]`. That is a queue `repairState` would
    now empty, so it now seeds this block's first two real rapid ids. The standing review load still survives a
    repair, and the check still compares the head's day count with the days the plan takes.
