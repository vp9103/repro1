## 4. Notes (outside this task, not acted on)

- **`__pathAudit().drillWhyOrphanKeys` lists every order-drill step (P2.6).** The audit builds
  `texts = new Set(d.items.map(i=>i[0]))`, and an order drill's items are strings, so `i[0]` is the first character.
  Every order-step why (the K13 data contract) is therefore reported as an orphan. On the stub that is the 6 steps of
  `d_rp8_order`. `pageAudit.nonEmpty` is `["drillWhyOrphanKeys"]` before and after this task. That fails P2.6's
  `pageAudit.nonEmpty == []`, and `drillItemsWithoutWhy` skips order drills entirely. The audit should key order drills
  by the step string and require a why for each step.
- **Pretest answers are held only in the DOM until every item is answered (pre-existing).** `S.pre` stores
  correctness, not the pick. A render in between, such as the cloze toggle or a sexp answer, redraws the pretest
  unanswered and lets an item be answered again.

### F9: read credit starts from the topic's own scroll position

**Defect 1. A topic reached from the bottom of another one got the old scroll credit.**
- *What the verifier saw.* rp8 recorded `scrolled` 0.934 while it sat at scrollY 0, and it was marked read without
  ever being scrolled.
- *Cause.* `go()` calls `render()` before `window.scrollTo(0)`. `render()` calls `wire()`, which calls `wireGrid()`,
  which calls `startDwell()`. `startDwell()` read `window.scrollY` straight away, and that was still the previous
  topic's position.
- *Fix.*
  - A topic that is not already being tracked starts at `dwellSeconds = 0` and `maxScrolled = 0`.
  - The first reading waits two animation frames, so `go()`'s scroll to the top and `restoreScroll()` have both run.
    After that, only real scroll events move `maxScrolled`.
  - Every way to switch topics goes through `go()`, then `render()`, then `startDwell()`: the rail, the next and
    previous buttons, search, and the `[data-t]` and `[data-gototopic]` links. So all of them are covered.
  - Only the same topic re-rendered in place (a sexp answer, the cloze toggle, a grid retake) keeps its running
    counters.
  - The interval now sets `dwellTimer = null` when it stops, so "same topic" means it is still being tracked.

**Defect 2. After the recall grid was scored, the chip still said "reading 8%".**
- *Cause.* The grid handler set `rec.read = true` but never touched `#dwellTag`. The dwell tick only painted the chip
  while `!rec.read`.
- *Fix.* `paintDwellTag(t)` paints the chip from the topic's record:
  - "read" in the good color when `rec.read`;
  - otherwise "reading N% · scrolled M%".

  It is called by the dwell tick, by the grid check handler and when `startDwell` runs. So a same-topic re-render no
  longer flashes "not read yet".

The read rule is unchanged: at least max(45 s, 0.35 × mins × 60) of visible dwell and at least 70 % scrolled, or a
scored grid.

### K13: the multi drill collapses to one column below 760 px

- *Cause.* The end-screen `.disc` and the running board's `.sortbtns` had an inline
  `grid-template-columns:repeat(3,1fr)`. No media query can override an inline style.
- *Fix.*
  - Both elements now carry `class="... dmulti" style="--dcols:N"`, where N = min(3, number of columns).
  - The shell has `.disc.dmulti,.sortbtns.dmulti{grid-template-columns:repeat(var(--dcols,3),minmax(0,1fr))}`.
  - `@media (max-width:760px){... minmax(0,1fr)}` makes it one column.
- *Sort end screen.* It already collapsed through `.disc`'s auto-fit, and it is unchanged.

### Notes (outside this task, not acted on)

- **Dwell credit and short pages.**
  - `rec.dwell` keeps the longest single continuous stay (`Math.max`). It does not add visits together.
  - A page shorter than the viewport can never reach `scrolled` 0.7, because scrollY / max(1, 0) = 0.
  - Both behaviors are unchanged. For a short page, the grid is the route to "read".
- **Old inflated values stay in storage.** `rec.scrolled` values saved before this fix, such as the verifier's rp8
  0.934, remain in that browser's storage. They cannot be told apart from real ones, so nothing repairs them.
- **Drill images do not load from the runtime folder.** When `.repro/runtime` is served, the stub multi-drill image
  (`repro-endo-assets/…`) does not load, because the assets are not next to the built page. This is a serving-layout
  issue, not an engine one.
